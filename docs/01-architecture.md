# KGgraph 基础架构设计

> 本文以**当前的最佳设计**为准，按功能点组织，不按时间线记录开发过程。每个功能点都附带设计思考与取舍：为什么是现在这个样子、放弃了哪些选项。

## 1. 定位：一个给 AI Agent 的确定性知识层

KGgraph 是一个 Go 实现的知识图谱 + 规则推理引擎，定位是 AI Agent 的「确定性知识 / 记忆层」：

- 用图表达规则型领域的条件关系（信号 → 状态 → 动作，含失效条件）
- 每条边可溯源到来源（`source_ref` + evidence）
- 决策被冻结为记录，用确定性规则重新评估，不依赖 LLM 的临场判断
- 通过 CLI / MCP 让 Agent 和人工都能使用

它围绕 LLM 的三个可观测失败模式设计：

| 失败模式 | KGgraph 的应对 |
| --- | --- |
| 幻觉（hallucination） | 事实和决策都带来源；`verify-edge` / `retire-edge` 管理可信度与时效 |
| 讨好（sycophancy） | `strict-ask` 只渲染已存规则算出的结论，决策时完全不调用 LLM |
| 不一致（inconsistency） | 决策冻结为记录、确定性重评估；冲突边在写入前被扫描 |

## 2. 设计目标

1. 确定性：同一输入 → 同一结论
2. 可审计：每个结论都能回溯到原文出处
3. 决策纪律：证据、反证、失效条件缺一不可
4. 本地优先：纯 Go SQLite，无外部数据库，离线可用
5. Agent 可用：MCP stdio server + 明确的工具边界
6. 演进可控：数据入库可验证、可重导、可移植

## 3. 核心设计：功能点与设计思考

### 3.1 图模型：节点、边、证据三层

**设计**：`kg_nodes`（id、node_type、aliases）、`kg_edges`（from/to、relation_type、polarity、confidence、condition_text、来源、时间窗、衰减、可执行标记）、`kg_edge_evidence`（原文摘录、supports/refute、weight）。边的有效性由 `observed_at / valid_from / valid_until` 管理。

**设计思考与取舍**：

- **为什么证据与边分离，而不是内联在边上**：结论（边）和依据（证据）需要独立演化——证据可以单独验证、失败、退休，而不必重写整条边。若证据内联，验证一个来源就要改动一条结论，审计链会断。
- **为什么边自带完整时间窗与衰减字段**（`decay_half_life_days`、`expires_at`）：知识有时效。命理规则千年不变，但市场判断、事件类事实会过期；把时效建模成字段而不是靠人工删除，「过期」才能成为可审计的动作。
- **为什么用 SQLite 而不是图数据库**：项目定位是本地 / 中小规模 Agent 记忆（千级节点），关系表完全够用，还免费获得事务、备份、纯 Go 跨平台。这是「先解决正确问题，不为未来规模提前买单」的取舍——真到十万级节点再评估图数据库，而不是一开始背上部署与运维成本。

### 3.2 来源与证据：每条边可审计

**设计**：每条边带 `source_ref`；`attach-edge-evidence` 挂证据；`verify-edge` 标记已验证 / 失败；`verify-evidence` 在语料中逐字核对证据。

**设计思考与取舍**：

- **为什么强制来源**：无来源的边在决策链路里没有意义。幻觉问题的根源是「结论与依据分离」，把两者绑死是最直接的对抗手段。
- **为什么区分逐字原文与概括标注**：AI 抽取时最隐蔽的数据污染，是把概括写成「原文引用」。逐字核对（忽略空白、标点、繁简差异）后，核对不上的如实标注为概括，宁可降低单条证据的展示可信度，也不让整库的可信度被污染。
- **为什么证据支持 refute（反驳）**：决策需要的不是「支持我的证据」，而是完整图景；反证挂在边上，评估时才能做平衡判断，而不是自我说服。

### 3.3 冲突即规则

**设计**：`conflict-scan` 确定性列出与候选边矛盾的活跃边；写入路径支持 `warn / block / off` 策略。

**设计思考与取舍**：

- **为什么冲突扫描必须确定性，而不是交给 LLM**：冲突判断本质是规则问题（相生 / 相克、支持 / 反对），规则引擎一次算完、结果可复现；交给 LLM 等于在关键路径上引入新的不可控点。
- **为什么默认 `warn`，而决策关键路径用 `block`**：严格程度应由场景决定。探索性知识允许矛盾存在（记录争议本身就是知识），但决策关键知识一旦静默矛盾，评估结果就不可信。把严格做成可配置策略而不是写死在代码里，用户按场景选择。

### 3.4 LLM 的边界：受限抽取，决策零 LLM

**设计**：`ingest-statement` 只把自然语言抽成严格 JSON；决策链路（`record-decision` → `evaluate-decision` → `strict-ask` → `pre-trade-check`）全程不调用 LLM。

**设计思考与取舍**：

- **为什么 LLM 只做抽取、不做判断**：抽取结果可验证、可回退；判断不可验证，同一问题每次答案都可能不同。把 LLM 放在「能被验证的一侧」，把确定性放在「不能出错的一侧」。
- **为什么要求严格 JSON 并拒绝未知字段**：抽取结果要写库，schema 漂移会污染数据；宁可这次抽取失败，不可静默写入错误结构。
- **置信度语义**：抽取置信度 = 把握度，不是事实概率。避免「AI 觉得是真的」被当成「数据证明是真的」。

### 3.5 写入路径：preview / confirm 拆分

**设计**：`ingest-preview`（抽取 + 冲突扫描，不写库）→ 调用方审查 → `ingest-confirm`（重新校验 + 重新扫描后才写）。

**设计思考与取舍**：

- **为什么写入前必须二次验证**：LLM 抽取不可信，且「预览」与「写入」之间状态可能变化；confirm 阶段重新校验，保证写进去的和审查过的完全一致，杜绝「预览通过、写入脏数据」的窗口。
- **为什么不提供「强制写入」捷径**：可靠性优先，便利性可以牺牲。低风险场景仍可用 `ingest-statement` 直写，但决策关键知识不提供跳过验证的路径。

### 3.6 决策记录与确定性评估

**设计**：`record-decision` 强制支持证据、反证、失效条件；`evaluate-decision` 产出确定性 verdict；`strict-ask` 措辞免疫；`pre-trade-check` 执行闸门。

**设计思考与取舍**：

- **为什么强制「反证」和「失效条件」**：只记支持证据的决策是自我说服。失效条件尤其关键——它定义了「什么情况下这个结论作废」，把结论从「观点」变成「可证伪的判断」。
- **为什么失效条件命中优先级最高**：条件一旦命中即 `invalidated`，无论原论点多合理。把止损 / 纠错变成规则，而不是依赖情绪或记忆力。
- **为什么 `strict-ask` 不调用 LLM**：反讨好。提问措辞、语气、压力都不改变结论；LLM 只允许在事后解释结论时出现，且不允许覆盖 `verdict` / `gate`。
- **为什么决策是记录而不是聊天**：聊天没有状态；记录才有审计（`decision-audit`）、统计与复盘（`decision-stats`）。

### 3.7 查询：精确 → 语义 → 多跳

**设计**：`lookup-context` 按「精确匹配 → 语义匹配（embedding，可选）→ 加权多跳展开」三层解析，返回路径与证据。

**设计思考与取舍**：

- **为什么精确优先**：节点 id 稳定、术语有别名；精确匹配保证「查木就是木」，语义匹配只作为兜底，避免歧义。
- **为什么语义可降级**：embedding 是可选能力，未配置时退化为精确 + 多跳，核心功能完全离线可用。这是「功能可选、核心不依赖外部服务」的取舍。
- **为什么多跳返回完整路径和证据**：给调用方（Agent / 人）的是推理依据，而不是一个孤立答案。

### 3.8 生命周期管理

**设计**：`retire-edge` 关闭边的有效性窗口，退休后不再参与推理；`reopen-edge` 恢复或延长。

**设计思考与取舍**：

- **为什么不直接删除**：删除丢失历史——谁、何时、为何说过这句话。退休保留记录但改变推理资格，审计完整。
- **为什么提供 reopen**：知识可能「暂时过期」后重新有效（例如事件条件解除）；用明确的动作恢复，而不是靠重建。

### 3.9 可移植性：export / import

**设计**：整个图序列化为 JSON 导出；导入时证据按边身份重新挂载。

**设计思考与取舍**：迁移后原始 id 可能冲突；按边身份（而非原始 id）重挂，保证证据不会挂错边。

## 4. 架构分层

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 接口层 | `cmd/kggraph`（CLI）、`mcp.go`（MCP stdio）、`graph_view.go`（本地图浏览器） | 三种入口，共用同一领域层 |
| 领域层 | `graph.go`、`ingest.go`、`lookup.go`、`conflict.go`、`decision.go`、`evaluate.go`、`pretrade.go`、`strict.go`、`stats.go`、`audit.go`、`transfer.go`、`storage.go` | 图、证据、冲突、决策、查询、审计、持久化 |
| 数据层 | SQLite（`modernc.org/sqlite`，纯 Go） | `kg_nodes` / `kg_edges` / `kg_edge_evidence` |
| 数据前端 | `internal/source` | 语料配置、搜索、抓取、清洗、简体化、质量验证 |

**设计思考**：领域层不感知入口。同一个 `Call` 既服务 CLI 也服务 MCP，行为天然一致；若三套入口各写一套逻辑，迟早会漂移出「CLI 能做、MCP 不能做」的差异。

## 5. 关键设计抉择汇总

| 抉择点 | 放弃的选项 | 选择 | 理由 |
| --- | --- | --- | --- |
| 持久化 | 图数据库 / 纯内存 | 纯 Go SQLite | 本地优先、跨平台、千级图足够、零运维 |
| 决策评估 | 每次调用 LLM | 确定性规则引擎 | 可复现、反讨好、可审计 |
| LLM 角色 | 决策者 | 受限抽取器 | 抽取可验证，判断不可验证 |
| 写入 | 预览直接写入 | preview → confirm 二次校验 | 防脏数据、防状态漂移 |
| 冲突处理 | 靠人发现 | 写入前确定性扫描 | 静默矛盾比没有知识更危险 |
| 严格程度 | 全局单一策略 | warn / block / off 场景化 | 探索允许争议，关键路径强制一致 |
| 证据标注 | 统一当原文 | 逐字 / 概括分型 | 保护全库可信度，宁可单条降级 |
| 时效处理 | 删除旧事实 | 时间窗 + 退休 | 保留审计，控制推理资格 |
| 语义查询 | 必需 embedding | 可降级离线 | 核心能力不依赖外部服务 |

## 6. 设计边界

- 不是图数据库的替代品：SQLite 定位本地 / 中小规模 Agent 记忆。
- 不是无约束聊天机器人：决策模式刻意严格、规则绑定。
- LLM 抽取仍可能引入噪音：判断关键场景请走 `record-decision`。
- 决策质量取决于输入的证据与失效条件：工具保证确定性，不保证输入一定正确。
