# 产品实践：周易八卦算术——训练数据工程案例

> 本文把「周易八卦算术」作为一个端到端的领域训练数据工程案例来呈现：从古籍原文到可审计、可复现、可混合的训练数据与评估基准，并最终支撑垂直模型。每个环节都标注「岗位能力对应」与「设计思考」。岗位要求与项目证据的总表见 [04-职业能力地图](04-career-direction.md)。

## 1. 产品定位

周易八卦算术是基于 KGgraph 引擎的术数命理分析工具，覆盖六爻、梅花易数、八字、紫微斗数、奇门遁甲、历法择吉等传统术数门类。

从用户侧看：结论来自带出处的规则，同一问题任何时候、任何问法结论一致，学派争议被显式标注，而不是模型临场发挥。

从岗位能力侧看：这个项目不是「算命网站」，而是一个「领域数据工厂 + 确定性评估器」。它最有价值的部分是数据如何被构造、清洗、验证、组织，以及这些数据未来如何变成 SFT / 偏好 / RL 训练数据与模型评估基准。前端网页与 Agent 只是数据与模型能力的出口。

产品形态（当前状态与规划）：

1. 已完成：古籍语料采集、清洗、验证、结构化入库（知识图谱 = 数据基础设施）
2. 下一阶段：从图谱生成训练数据（SFT / 偏好 / Agent 轨迹）；前端网页 + 用户交互
3. 未来：小模型后训练实验（SFT、DPO / GRPO、模型合版与遗忘分析）；Agent 接入

## 2. 为什么这个领域适合展示数据工程能力

命理是典型的「高熵符号系统」：五行生克、干支冲合刑害、十神、四柱排盘、大运流年、六爻体用都是规则，但组合爆炸、流派众多。对数据工程而言，这恰恰是理想的练兵场：

- **数据构造有真实难度**：术语多（身强 / 身旺）、流派多（子平 / 滴天髓）、矛盾多（相生与相克必须条件化）——正好覆盖 SFT 数据构造中的歧义消解与条件化标注
- **数据质量可客观验证**：证据逐字核对、冲突扫描都是可量化的 QC 手段，不需要主观打分
- **天然具备 ground truth**：古籍原文 + 机制性规则是确定性的，可以生成正反样本、构造偏好对、设计奖励信号

## 3. 数据流水线：每一环都是数据工程能力

### 3.1 语料采集：数据源管理与选样

**做法**：三源并用（维基文库 / ctext / 易海观要），31 部古籍，覆盖卦爻、八字、紫微、六壬、奇门、择吉、相法等门类；每书带来源与章节 manifest。

**岗位能力对应**：多源数据收集、来源管理与版本记录。

**设计思考**：不依赖单一来源，避免一本书的版本问题拖垮整条链；分书管理才能逐本验证、逐本重导。

### 3.2 清洗：数据清洗工程

**做法**：维基文本 → 纯文本（模板、引用、标签剥离）；繁体 → 简体统一（OpenCC）。

**岗位能力对应**：清洗规则设计（确定性正则优先，保证可复现）；字符集 / 编码一致性处理。

**设计思考**：清洗用确定性规则而不是 LLM——可复现、不会随机漏行；繁转简在源头做，避免同一概念两种写法造成重复数据。

### 3.3 验证：质量过滤与 QC

**做法**：替换字符、私用区字形、中文占比异常检测；证据逐字核对门（忽略空白、标点、繁简差异），核对不上的如实标注为概括而非原文。

**岗位能力对应**：SFT 数据的质量过滤与幻觉抑制；数据真实性审计。

**设计思考**：质量门在批量前设好——批量铺开后修数据比设门贵得多；诚实标注（逐字 vs 概括）比「看起来完整」重要，这是数据可信度的底线。

### 3.4 结构化入库：标注与版本管理

**做法**：每书一个抽取脚本 → `ingest/<slug>.json`（nodes/edges/evidence），与 `kggraph import-graph` 兼容；按 `ingest/batches.txt` 顺序导入；重导先清库再全量按序执行。

置信度分层：

- 机制性规则（五行生克、排盘、冲合、历法）：0.85-0.95
- 经验断语（神煞吉凶、体用吉凶）：0.55-0.75，并标注条件 / 争议

**岗位能力对应**：结构化标注 schema 设计；数据集版本管理与可复现构建。

**设计思考**：分批次 = 可审查、可回滚、可单书重跑；置信度分层避免把「确定规则」和「参考断语」混在一起，这正是训练数据难度分层的基础。

## 4. 从图谱到训练数据：四条数据产线

本节严格区分「已具备」与「规划中」，不把规划当已有经验。

### 4.1 SFT 数据产线（已具备基础，产线规划中）

- 已具备：规则、置信度、条件文本、证据——SFT 样本所需的要素都在图里
- 规划：把「问题 → 规则路径 → 带出处的回答」渲染成指令样本；置信度分层做难度分层；条件文本做上下文约束；证据做引用格式
- 验证：小批量人工审阅（沿用小步验证方法论）→ 与原文一致性检查 → 全量生成

### 4.2 Preference / RL 数据（规划中，有确定性基础）

- 已具备：确定性评估器（evaluate / strict-ask / pre-trade-check）可当作规则式 reward 原型；`invalidates` 边表达争议
- 规划：用图谱 ground truth 构造偏好对（基于规则的正答 vs 幻觉 / 遗漏的反答）；争议规则设计「条件化样本」；人工偏好标注闭环（preview/confirm 机制直接复用）
- 验证：偏好一致性（同题同偏好）、模型在评估集上的胜率

### 4.3 Agent Trajectory 数据（已具备基础，生产规划中）

- 已具备：MCP 工具集（kg_*）、确定性闸门约束 Agent 行为、`decision-audit` 记录决策轨迹
- 规划：记录 Agent 调用工具解决问题的完整轨迹（多轮、含中间工具输出）；用图谱验证轨迹终点的结论是否 grounded
- 验证：轨迹完成率、结论与图谱一致率

### 4.4 数据混合与效果分析（已具备基础设施，实验规划中）

- 已具备：批次台账（batches.txt）、每书节点 / 边 / 证据统计、conflict-scan 一致性指标
- 规划：按门类（卦爻 / 八字 / 紫微 / 六壬）、难度（置信度）、长度（证据条数）设计混合比例实验；以图谱查询命中率与一致性作为效果指标
- 验证：消融对比——不同混合比例的 SFT 模型在固定评估集上的表现

## 5. 当前查询能力

| 能力 | 命令 | 用途 |
| --- | --- | --- |
| 上下文查询 | `kggraph lookup-context --term "身强"` | 术语精确匹配 + 多跳展开，结果带证据 |
| 冲突检查 | `kggraph conflict-scan --from-id "木" --to-id "火" --relation-type 相克` | 检查两条规则是否自相矛盾 |
| 规则展开 | `kggraph expand-reasoning` | 从任一概念展开规则路径 |
| 可视化 | `kggraph graph-view`（http://127.0.0.1:8787） | 本地调试图谱结构 |

**设计思考**：`lookup-context` 返回推理路径和证据而不是孤立答案，这是评估「模型回答是否 grounded」的对照基准；冲突检查保证图谱内部一致，对应训练数据的一致性校验；`graph-view` 是开发调试工具，不是产品前端。

## 6. 产品规划：从数据到模型

- 阶段一（已具备）：语料 → 图谱：数据基础设施
- 阶段二（规划）：SFT 数据产线 + 小模型 SFT + 图谱评估
- 阶段三（规划）：偏好 / RL 数据 + DPO / GRPO 实验；Agent 轨迹数据 + Function Calling 评估
- 阶段四（规划）：多领域模型合版——checkpoint 分析、SFT vs RL 对比、能力回退与遗忘检测；图谱确定性评估器是这套实验的验证工具
- 出口：前端网页 + 用户交互；Agent 接入

## 7. 边界与责任

- 周易命理是传统文化知识体系，不是科学结论；工具定位是文化学习与分析辅助
- 明确告知：不构成医疗、财务、法律或重大人生决策的依据
- 确定性 ≠ 正确性：输出质量取决于语料与规则的验证质量
- 诚实声明：训练与模型合版实验属规划阶段，投递与面试中不冒充已完成经验；已可演示的是语料 → 图谱的数据工程能力
