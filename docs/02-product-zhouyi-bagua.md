# 产品实践：周易八卦算术

> 本文以「周易八卦算术」作为 KGgraph 的实践产品。内容以当前最佳方案为准，覆盖数据流水线、当前能力与产品规划；每个环节都附「为什么这样做」的设计思考。

## 1. 产品定位

周易八卦算术是一款基于 KGgraph 引擎的术数命理分析工具，覆盖六爻、梅花易数、八字、紫微斗数、奇门遁甲、历法择吉等传统术数门类。

与「直接问 AI」的算命产品不同：

- 每个结论都来自图谱中带出处的规则，不是模型临场发挥
- 同一问题在任何时候、任何问法下得到同一结论
- 学派争议、经验断语被显式标注置信度和适用条件

产品形态（当前状态与规划，非开发日志）：

1. 已完成：古籍语料采集、清洗、验证、结构化入库（知识图谱）
2. 下一阶段：前端网页 + 用户交互逻辑
3. 未来：接入 Agent，让用户通过对话获得可靠分析

## 2. 为什么命理适合图谱 + 确定性规则

命理是典型的「高熵符号系统」：五行生克、干支冲合刑害、十神、四柱排盘、大运流年、六爻体用……都是规则，但组合爆炸、流派众多。LLM 直接回答容易把规则记混、把出处编错。

图谱方案的三个优势：

1. **规则可组合**：五行 → 生克 → 十神 → 格局 → 断语，形成多跳推理路径
2. **出处可审计**：每条边挂原文证据，断语可回原文核对
3. **争议可管理**：低置信度 + `invalidates` 边表达流派分歧，而不是把分歧抹平

## 3. 数据流水线

### 3.1 语料：31 部古籍

**做法**：三源并用——维基文库（zh.wikisource）、ctext、易海观要（yihaiguanyao）。书目覆盖卦爻、八字、紫微、六壬、奇门、择吉、相法等门类，包括周易、周易正义、周易本义、易学启蒙、易传、周易集解、易纬乾坤凿度、五行大义、渊海子平、滴天髓（阐微）、穷通宝鉴、子平真诠、神峰通考、三命通会、星平会海、星学大成、张果星宗、梅花易数、增删卜易、卜筮正宗、火珠林、京氏易传、焦氏易林、皇极经世、协纪辨方书、紫微斗数全书、六壬指南、六壬大全、烟波钓叟歌、麻衣相法等。

**设计思考**：

- 三源并用的取舍：维基文库开放、正文完整；ctext 结构化、可按章节定位；易海观要补缺。不依赖单一来源，避免一本书的版本质量问题拖垮整条链。
- 为什么不合并成一个大文件：分书管理才能逐本验证、逐本重导；合集会掩盖单书质量问题，出问题也难以定位。

### 3.2 清洗

**做法**：维基文本 → 纯文本（模板、引用、标签剥离）；繁体 → 简体统一（OpenCC）。

**设计思考**：

- 清洗用确定性规则而不是 LLM：可复现，不会「偶尔漏一行」；同一批语料任何时候清洗结果一致。
- 繁转简在源头做：同一概念两种写法会造成重复节点、证据核对失败；在源头统一比在库内清洗便宜，也保证证据与语料一致。

### 3.3 验证

**做法**：

- 文本质量检查：替换字符、私用区字形、中文占比异常检测
- 证据门：每条证据 snippet 在语料中逐字核对（忽略空白、标点、繁简差异）；核对不上的如实标注为概括证据，不冒充原文

**设计思考**：

- 质量门在批量前设好：批量一旦铺开，修数据比设门贵得多。
- 为什么「概括」和「逐字引用」必须分型：AI 抽取最隐蔽的问题是把概括写成原文引用；分型后用户能区分「原话」和「转述」，工具的可信度建立在数据是否诚实上。

### 3.4 结构化入库

**做法**：每本书一个抽取脚本 → `ingest/<slug>.json`（nodes/edges/evidence），与 `kggraph import-graph` 兼容；按 `ingest/batches.txt` 的顺序导入 SQLite；重导先清库再全量按序执行。

置信度分层：

- 机制性规则（五行生克、排盘、冲合、历法）：0.85-0.95
- 经验断语（神煞吉凶、体用吉凶）：0.55-0.75，并标注条件 / 争议

**设计思考**：

- 为什么分批次而不是一次性大导入：每批可审查、可回滚、可单书重跑；批次清单（`batches.txt`）本身就是可复现的入库顺序。
- 为什么置信度分层：机制是确定规则（生克关系、排盘步骤），经验断语依赖语境（同样一个神煞在不同格局里吉凶不同）。混在一起会让整库置信度失真，也误导用户区分「确定规则」和「参考断语」。

## 4. 当前查询能力

| 能力 | 命令 | 用途 |
| --- | --- | --- |
| 上下文查询 | `kggraph lookup-context --term "身强"` | 术语精确匹配 + 多跳展开，结果带证据 |
| 冲突检查 | `kggraph conflict-scan --from-id "木" --to-id "火" --relation-type 相克` | 检查两条规则是否自相矛盾 |
| 规则展开 | `kggraph expand-reasoning` | 从任一概念展开规则路径 |
| 可视化 | `kggraph graph-view`（http://127.0.0.1:8787） | 本地调试图谱结构 |

**设计思考**：

- `lookup-context` 为什么是主入口：命理术语别名极多（身强 / 身旺、木 / 甲乙），精确 + 多跳返回的是推理路径和证据，而不是一个孤立答案。
- 冲突检查为什么对命理特别重要：五行生克是整库最容易被写矛盾的规则集（相生与相克同时成立必须带条件）；写入前扫描保证图谱内部一致。
- 为什么做本地可视化：人工核对图谱结构时，颜色区分活跃 / 退休 / 冲突边，比翻 JSON 高效得多。它是开发调试工具，不是产品前端。

## 5. 产品规划

### 5.1 前端网页 + 用户交互（下一阶段）

**形态**：

- 输入：出生时间与地点（八字排盘）、问题或起卦方式（六爻 / 梅花）
- 引擎：排盘与断语规则已在图谱中，前端调用确定性工具取结论
- 输出：结论 + 引用的原文出处 + 置信度 + 适用条件 + 争议标注

**设计思考**：

- 为什么先做交互验证再铺开：命理结论的呈现方式（出处、置信度、条件）直接决定用户是否信任工具；先做一个页面、一条交互，验证展示符合预期，再扩展功能。
- 产品前端与 `graph-view` 的关系：`graph-view` 面向开发调试，产品页面面向用户，展示层独立设计，不共用一套界面。

### 5.2 Agent 接入（未来）

**形态**：`kggraph serve-mcp` 提供 MCP stdio server；Agent 只能调用确定性工具（lookup / strict 系列），不能自由发挥断语；用户在对话中获得可追溯、可复核的答案。

**设计思考**：产品的可靠性承诺来自「结论可溯源、可复现」。如果允许 Agent 在确定性结果之外自由发挥，等于把 LLM 的不可控性重新引入产品。因此接入顺序固定为：先确定性工具 → 验证输出质量 → 再开放对话。

## 6. 边界与责任

- 周易命理是传统文化知识体系，不是科学结论；工具定位是文化学习与分析辅助
- 明确告知：不构成医疗、财务、法律或重大人生决策的依据
- 确定性 ≠ 正确性：输出质量取决于语料与规则的验证质量——这正是本项目持续投入清洗与验证的原因
