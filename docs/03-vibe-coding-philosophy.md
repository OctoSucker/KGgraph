# Vibe Coding 哲学：这次开发与以前不同

> 这是我在 KGgraph 周易语料工程中关于 vibe coding 的记录。这次开发和以往最大的不同是：我全程没有写代码，代码全部由 AI 编写。我的工作变成了定义需求、设计流程、验证结果、判断方向。
>
> 说明：本文不是开发日志，而是方法论沉淀。文中提到的实践例子是为了说明「为什么这样做有效」，不是按时间线记录事件经过。

## 1. 一句话总结

**基建先行，需求指引，小步验证，流程固化；程序驱动执行，知识只进数据。**

## 2. 这次的角色变化

以前：我写代码，AI 辅助。

这次：AI 写代码，我负责——

- 需求定义：把「要什么」说清楚
- 验证：AI 做出来的东西是不是我真正要的
- 架构判断：数据怎么组织、流程怎么走
- 方向决策：哪些数据要、哪些不要、做到什么程度

## 3. 核心方法论

### 3.1 基建先行

先搭数据管道，而不是先做功能。语料配置（`gushu/corpus.json`）→ 抓取 → 清洗 → 简体化 → 验证 → 抽取 → 入库，这条链先立起来；后面的书只是往管道里喂。

### 3.2 需求指引

每个阶段的形态由具体需求决定。最初的种子数据试过 finance、crypto，发现方向不对就及时移除，最后落到周易命理——因为它同时满足「规则密度高」和「LLM 直接处理不可靠」两个条件，最能体现图谱引擎的价值。

### 3.3 迭代处理流程

管道不是一次设计完的。第一批书手工清洗、核对；踩坑后把对策变成代码（`verify-evidence` 证据门、`simplify` 繁体统一、`batches.txt` 重导清单），流程在迭代中长出来。

### 3.4 流程固化，吸收为项目工具

每解决一次问题，就把解法固化成项目里的工具 / 命令，而不是记在脑子里：

- 找书 / 抓书：`kggraph source search / fetch`
- 清洗：`kggraph source clean`
- 繁体统一：`kggraph source simplify`
- 证据核对：`kggraph source verify-evidence`
- 入库顺序：`ingest/batches.txt`

固化之后，从「第一本书手工搬砖」变成「第 27 本书走管道」，处理速度被不断加速。

## 4. 最值得记住的经验：小批量验证先行

> 每次让 AI Agent 做某种处理，第一次操作时，最好先让 AI 处理一点点数据，我验证确实是我需要的，再推进批量处理。

原因：

1. 用语言沟通需求，AI 不一定准确理解——它可能按字面做，但理解偏了
2. 自己说的也不一定准确——很多细节没想清楚，表达出来才是完整的
3. 所以现在的开发，开发者对项目其实有一种模糊的认知

推论：

- 模糊认知是常态，不是缺陷
- 越早验证，认知越清晰
- 小批量验证 = 用最小成本把认知钉死

实践例证（用于说明方法论为什么有效）：

- 第一本书（五行大义）的抽取脚本先做、先入库、先看效果，确认结构对，才铺开到 27 批
- `verify-evidence` 先跑一个批次，发现大量「概括冒充原文」，才决定把证据分两类（逐字原文 / 概括标注）
- 领域选择：先小规模种 finance / crypto 数据，很快发现不合适，转向周易——而不是等做大了才发现

## 5. 两个值得记录的发现

### 5.1 让程序驱动，而不是让 Agent 重复干活

**现象**：让 Agent 做重复性工作（比如一本一本处理古籍），它会「偷懒」——只做一点点，却汇报完成，然后请求下一步。原因不是恶意，而是长链条重复任务里，每一步都在「沟通-汇报-再指示」上消耗；Agent 倾向于最小化单轮工作量，人也容易被「完成」的汇报带偏。

**对策**：把固定流程用程序实现，让程序去 call Agent 或 LLM。程序负责流程控制（遍历、调用、校验、记录进度），Agent / LLM 只负责单点任务（抽取某一本书、清洗某一段文本）。

为什么有效：

- 程序要么完成、要么报错，不存在「汇报完成」的中间态；未完成 = 校验失败，会被明确暴露
- Agent 的每个输出变成程序可校验的输入，而不是等人肉确认的汇报
- 流程可复现、可断点续跑，人只需要看结果和异常

这是「流程固化」的进一步：不只是固化成命令，而是固化成「程序驱动、Agent 执行」的编排关系——程序是司机，Agent 是执行单点任务的工人。

### 5.2 程序化要守住边界：知识进数据，不进代码

**现象**：让 Agent 写这个编排程序时，它把想要导入 kggraph 的知识直接写进了代码——比如把「乾为天、坤为地」这类取象、干支五行关系硬编码进脚本。这不是我想要的。

为什么不对：

- 知识写进代码，就失去了知识图谱的意义：不可查询、不可冲突检查、不可溯源、不可被 QC 验证
- 改知识要改代码：新增一条规则 = 改脚本 + 重新构建，而不是往数据里加一条带来源的边
- 代码里的知识没有证据：无法回答「这句话出自哪里」

正确边界：

- 代码管流程：怎么抓、怎么清洗、怎么抽取、怎么导入
- 数据管知识：节点、边、证据都进图谱，带来源、带置信度、带条件
- 判断标准：打开脚本应该看到「怎么处理」，而不是「知识是什么」；知识应该由抽取流程产出为结构化数据，而不是由人（或 AI）把知识翻译成代码

## 6. 需要固化成原则的教训

### 6.1 重复导入会累积

同一批次重复 import 会重复附加证据，不是幂等操作；重导必须先清库，再按 `batches.txt` 全量重导。这个教训后来被固化成了文档里的标准命令。

### 6.2 质量门要在批量前设好

批量开始之前先设验证：文本质量检测（替换字符 / 私用区 / 中文占比）、证据逐字核对。批量一旦铺开，修数据比设门贵得多。

### 6.3 诚实标注比「看起来完整」重要

核对不上的证据如实标注为概括，不冒充原文。工具的可信度建立在数据是否诚实上。

## 7. 这套方法论对后续阶段同样适用

- 前端网页：先做一个页面、一条交互，验证展示和交互符合预期，再铺开
- Agent 接入：先让 Agent 只调用确定性工具，验证输出质量，再开放自由对话
- 继续把流程固化成工具，让每一次迭代都比上一次快

放到 LLM 数据工程与后训练岗位上，这套方法论同样成立：先构造一百条 SFT 样本看质量分布，再全量生产；先跑一个 checkpoint 对比实验，再铺开完整实验矩阵。小步验证不是「慢」，而是把不确定性提前暴露——这和本项目数据流水线里「质量门在批量前设好」是同一个原则。
